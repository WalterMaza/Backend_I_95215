Sección 1

Refactorizar: reorganizar lo que ya funciona

Esta semana el cambio principal está dentro de la aplicación.

La API de la clase anterior ya recibe peticiones con Express, separa rutas y controllers y guarda servicios y reservas en archivos JSON. Ahora vamos a repartir las responsabilidades de los managers.

Antes

El controller llama a un manager que prepara datos y accede al archivo.

controller → manager → JSON

Ahora

Separamos decisiones, acceso a datos y persistencia.

controller → service → repository → DAO → JSON

Refactorizar significa mejorar la estructura interna sin cambiar el comportamiento observable. Si antes una consulta devolvía determinados datos, debería seguir devolviéndolos después.

Una cosa por vez

Primero reorganizamos una consulta. Después recorremos una creación y finalmente una actualización. No necesitamos cambiar a clases ni agregar una base de datos para entender las capas.

¿Qué cambia en la base de la clase 4?

ParteCambio
routesConserva sus URLs y métodos.
controllersPasa a importar funciones de services.
managersSus responsabilidades se reparten en tres capas.
dataSigue guardando archivos JSON.
pasosSe elimina junto con sus comandos del package.json.

Agregar una validación nueva también cambia el comportamiento para las entradas inválidas. Conviene distinguir ese cambio del refactor y probarlo por separado.

Sección 2

Cada capa responde una pregunta

La separación depende del trabajo que hace el código, no solamente del nombre de la carpeta.

CapaPreguntaEjemplo
Router¿Qué función atiende esta URL?Conectar un GET con un controller.
Controller¿Qué llegó por HTTP y qué respondo?Leer req.params y responder 200 o 404.
Service¿Qué debe permitir o hacer el sistema?Validar un nombre, proteger un ID, acumular cantidades.
Repository¿Cómo ofrezco acceso a estos datos?Exponer getAll() y delegar en el DAO elegido.
DAO¿Cómo consulto y guardo en esta persistencia?Leer, parsear y escribir un archivo JSON.

DAO: Data Access Object

Es la capa que conoce FileSystem: la ruta del archivo, readFile, JSON.parse y writeFile. Puede buscar un registro o guardarlo. No decide si una cantidad debe incrementarse por una regla del sistema.

Repository: el punto de acceso a los datos

El service le pide una operación al repository. El repository la delega en el DAO. Al principio, sus funciones pueden parecer repetitivas porque solo conectan ambas partes.

Más adelante podríamos cambiar el DAO utilizado. Para que las otras capas sigan funcionando, el nuevo DAO deberá respetar las operaciones y los resultados esperados.

Service: las decisiones del sistema

Recibe datos normales de JavaScript y devuelve resultados. Puede consultar varios repositories para aplicar una regla, pero no abre archivos ni utiliza res.status().

“Services” puede significar dos cosas

En el proyecto, servicio es un recurso, como una consulta médica. En arquitectura, la capa service contiene reglas de negocio. Por eso también existe un bookings.service.js: contiene las reglas de las reservas.

Sección 3

Las capas siguen siendo funciones

Una función llama a otra. Los argumentos llevan datos y los return traen resultados.

Ejercicio 2 · Un recorrido sin archivos

Seguir el dato de ida y de vuelta

Este ejemplo se ejecuta como un único archivo JavaScript. El array representa una fuente de datos temporal.

const datos = [{ id: "a1", name: "Cuaderno" }]

function daoGetAll() {
  console.log("3. DAO")
  return datos
}

function repositoryGetAll() {
  console.log("2. Repository")
  return daoGetAll()
}

function getArticles() {
  console.log("1. Service")
  return repositoryGetAll()
}

console.log(getArticles())

// 1. Service
// 2. Repository
// 3. DAO
// [{ id: "a1", name: "Cuaderno" }]

La última función obtiene los datos. Después, cada return entrega ese resultado a quien hizo la llamada.

Ejercicio 3 · Detectar un return faltante

¿Por qué aparece undefined?

function repositoryGetAll() {
  daoGetAll()
}

console.log(repositoryGetAll()) // undefined

El DAO se ejecutó, pero el repository no devolvió su resultado. La solución es:

function repositoryGetAll() {
  return daoGetAll()
}

¿Qué cambia cuando aparece async?

async function daoGetAll() {
  return [{ id: "a1", name: "Cuaderno" }]
}

async function repositoryGetAll() {
  return daoGetAll()
}

async function getArticles() {
  const articles = await repositoryGetAll()
  return articles
}

console.log(await getArticles())

Una función async siempre devuelve una promesa. Usamos await cuando necesitamos trabajar con el resultado resuelto.

¿Por qué el repository no tiene await?

return daoGetAll() devuelve la promesa y permite que quien llama la espere. En una función que solo delega, no hace falta agregar await. Si necesitamos examinar el array antes de devolverlo, sí debemos esperar el resultado.

Importar funciones bajo un nombre

import * as repository from "../repositories/articles.repository.js"

const articles = await repository.getAll()

import * as repository agrupa las exportaciones del módulo bajo el nombre repository. No crea una clase. También podríamos importar una función específica:

import { getAll } from "../repositories/articles.repository.js"

const articles = await getAll()

import fs from "fs/promises"
import path from "path"
import { fileURLToPath } from "url"

// Conservamos la forma de construir rutas de la clase anterior.
const __filename = fileURLToPath(import.meta.url)
const __dirname = path.dirname(__filename)
const FILE_PATH = path.join(__dirname, "../data/articles.json")

export async function getAll() {

Ejercicio 6 · Validar sin Express

    
Probar primero una función pequeña

    
Este ejercicio es independiente. Permite entender la validación antes de conectarla al mini proyecto.

    
function validateArticle(data) {
  if (!data || typeof data.name !== "string" || !data.name.trim()) {
    throw new Error("El nombre es obligatorio")
  }

  if (typeof data.price !== "number" ||
      !Number.isFinite(data.price) ||
      data.price < 0) {
    throw new Error("El precio debe ser un número mayor o igual a cero")
  }

  return {
    name: data.name.trim(),
    price: data.price
  }
}

console.log(validateArticle({ name: " Cuaderno ", price: 0 }))
// { name: "Cuaderno", price: 0 }

try {
  validateArticle({ name: "", price: 100 })
} catch (error) {
  console.log(error.message) // El nombre es obligatorio
}

    
throw interrumpe la función. El código posterior no se ejecuta y el error puede capturarse con catch. trim() permite detectar un nombre formado solamente por espacios.

    

      
Un precio de cero puede ser válido

      
if (!data.price) rechazaría el cero porque es falsy. Conviene comprobar el tipo y el rango que realmente necesitamos.

    

  


  

    
Ejercicio 7 · Conectar POST con todas las capas

    
Agregar POST /api/articles


    
Agregar al DAO

    
// Función interna: no necesita exportarse.
async function saveAll(articles) {
  await fs.writeFile(FILE_PATH, JSON.stringify(articles, null, 2))
}

export async function create(data) {
  const articles = await getAll()

  articles.push(data)
  await saveAll(articles)

  return data
}

    
El DAO recibe un artículo preparado. Solo lo incorpora al array y guarda.


    
Agregar al repository

    
export async function create(data) {
  return dao.create(data)
}


    
Agregar el import y las funciones al service

    
import { randomUUID } from "crypto"

// Función interna del service.
function validateArticle(data) {
  if (!data || typeof data.name !== "string" || !data.name.trim()) {
    const error = new Error("El nombre es obligatorio")
    error.code = "INVALID_DATA"
    throw error
  }

  if (typeof data.price !== "number" ||
      !Number.isFinite(data.price) ||
      data.price < 0) {
    const error = new Error("El precio debe ser un número mayor o igual a cero")
    error.code = "INVALID_DATA"
    throw error
  }

  return {
    name: data.name.trim(),
    price: data.price
  }
}

export async function createArticle(data) {
  const validData = validateArticle(data)

  const article = {
    id: randomUUID(),
    name: validData.name,
    price: validData.price
  }

  return repository.create(article)
}

    
error.code es una propiedad que agregamos al objeto de error. La etiqueta permite que el controller reconozca un problema de validación sin comparar el texto del mensaje.

    
El service no asigna un status HTTP: informa qué ocurrió. El controller decide cómo responder.


    
Agregar al controller

    
export async function controllerCreate(req, res) {
  try {
    const article = await service.createArticle(req.body)

    return res.status(201).json({
      status: "success",
      data: article
    })
  } catch (error) {
    if (error.code === "INVALID_DATA") {
      return res.status(400).json({
        status: "error",
        message: error.message
      })
    }

    return res.status(500).json({
      status: "error",
      message: "No se pudo guardar el artículo"
    })
  }
}


    
Agregar al router, antes de export default

    
router.post("/", controller.controllerCreate)


    
Probar desde un cliente HTTP

    
Enviar un POST a http://localhost:8080/api/articles, con body JSON y encabezado Content-Type: application/json:

    
{
  "name": "Lapicera",
  "price": 800
}

    
Debería responder 201, devolver el ID generado y agregar el artículo al archivo.

    
Si enviamos { "name": "", "price": 800 }, debería responder 400 y no escribir el artículo.

Ejercicio 8 · Actualizar y proteger el ID

    
Agregar PUT /api/articles/:aid

    
En este ejercicio, PUT recibe todos los campos editables: name y price. El ID de la URL identifica al recurso y no se modifica.


    
Agregar al DAO

    
export async function update(id, data) {
  const articles = await getAll()
  const index = articles.findIndex(article => article.id === id)

  if (index === -1) return null

  articles[index] = data
  await saveAll(articles)

  return articles[index]
}


    
Agregar al repository

    
export async function update(id, data) {
  return dao.update(id, data)
}


    
Agregar al service

    
export async function updateArticle(id, data) {
  const current = await repository.getById(id)

  if (!current) return null

  const validData = validateArticle(data)

  // Construimos los campos permitidos y conservamos la identidad.
  const updated = {
    id: current.id,
    name: validData.name,
    price: validData.price
  }

  return repository.update(id, updated)
}


    
Agregar al controller

    
export async function controllerUpdate(req, res) {
  try {
    const { aid } = req.params
    const article = await service.updateArticle(aid, req.body)

    if (!article) {
      return res.status(404).json({
        status: "error",
        message: "Artículo no encontrado"
      })
    }

    return res.status(200).json({
      status: "success",
      data: article
    })
  } catch (error) {
    if (error.code === "INVALID_DATA") {
      return res.status(400).json({
        status: "error",
        message: error.message
      })
    }

    return res.status(500).json({
      status: "error",
      message: "No se pudo actualizar el artículo"
    })
  }
}


    
Agregar al router

    
router.put("/:aid", controller.controllerUpdate)

export async function remove(id) {

}

Cómo quedan las operaciones

  

    

      
OperaciónServiceRepository y DAO

      
        
ListargetArticles()getAll()

        
BuscargetArticleById(id)getById(id)

        
CrearcreateArticle(data)create(data)

        
ActualizarupdateArticle(id, data)update(id, data)

Usamos remove porque delete es una palabra reservada y no puede ser el nombre de una declaración function delete(). Si se necesita exponer exactamente el nombre delete, ESM permite un alias:

  
// Agregado al módulo que ya exporta remove:
export { remove as delete }

// Desde otro módulo:

Es un nombre alternativo para la misma función, no una operación diferente.

function addMaterialToList(list, material) {

Ejercicio 13 · Crear y consultar una lista vacía

    
Preparar la entidad desde el service

    
Fragmento para lists.service.js. Supone un repository de listas con create, getById y update, que delega en un DAO de JSON con el mismo patrón ya practicado.

    
import { randomUUID } from "crypto"
import * as listsRepository from "../repositories/lists.repository.js"

export async function createList() {
  const list = {
    id: randomUUID(),
    items: []
  }

  return listsRepository.create(list)
}

export async function getListById(id) {
  return listsRepository.getById(id)
}

    
La decisión de que una lista nueva comience vacía pertenece al service. El DAO recibe { id, items: [] } y lo guarda.

  


  

    
Ejercicio 14 · Consultar dos repositories

    
La regla completa dentro de un service

    
Agregar al mismo lists.service.js. El repository de materiales necesita getById; el de listas, getById y update.

    
import * as materialsRepository from "../repositories/materials.repository.js"

export async function addMaterialToList(listId, materialId) {
  const list = await listsRepository.getById(listId)

  if (!list) {
    const error = new Error("Lista no encontrada")
    error.code = "NOT_FOUND"
    throw error
  }

  const material = await materialsRepository.getById(materialId)

  if (!material) {
    const error = new Error("Material no encontrado")
    error.code = "NOT_FOUND"
    throw error
  }

  const existing = list.items.find(
    item => item.material === materialId
  )

  if (existing) {
    existing.quantity += 1
  } else {
    list.items.push({
      material: materialId,
      quantity: 1
    })
  }

  return listsRepository.update(listId, list)
}

    
El service consulta dos fuentes de datos a través de sus repositories. Aplica la regla y finalmente pide guardar. El DAO de listas no necesita saber por qué cambió la cantidad.


    
Controller que traduce el resultado a HTTP

    
import * as service from "../services/lists.service.js"

export async function controllerAddMaterial(req, res) {
  try {
    const { lid, mid } = req.params
    const list = await service.addMaterialToList(lid, mid)

    return res.status(200).json({
      status: "success",
      data: list
    })
  } catch (error) {
    if (error.code === "NOT_FOUND") {
      return res.status(404).json({
        status: "error",
        message: error.message
      })
    }

    return res.status(500).json({
      status: "error",
      message: "No se pudo actualizar la lista"
    })
  }
}


    
Conexión desde un router de listas

    
router.post("/:lid/materials/:mid", controllerAddMaterial)

// Si el router se monta en /api/lists:
// POST /api/lists/l1/materials/m1

    
El router conecta la operación; el controller obtiene los dos parámetros. La lógica de sumar cantidades permanece dentro del service.

Errores que conviene reconocer

  

    

      
El dato no vuelve

      
Revisar los return del DAO, repository y service. Ejecutar una función no implica devolver lo que produjo.

    

    

      
El resultado es una promesa

      
Antes de usar find o de construir la respuesta con los datos, esperar la operación asíncrona con await.

    

    

      
El service usa res

      
La regla quedó atada a Express. El service devuelve datos o lanza un error; el controller elige la respuesta HTTP.

    

    

      
El DAO suma cantidades repetidas

      
Esa es una regla del sistema. El service debe calcular la nueva colección y enviarla al DAO mediante el repository.

    

  


  
¿Qué pasa si el JSON está roto?

  
JSON.parse lanza un error. El DAO lo propaga, la promesa se rechaza y el controller lo captura. No debe confundirse un archivo dañado con una colección vacía.


  
Las capas no solucionan la concurrencia

  
Dos peticiones todavía pueden leer el mismo JSON y sobrescribir los cambios de la otra. Este material utiliza operaciones secuenciales para aprender. Separar las capas organiza el código, pero no agrega transacciones ni convierte un archivo en una base de datos.


  

    
Refactor y comportamiento

    
Compará las mismas peticiones antes y después de reorganizar el proyecto. Si cambió una URL, el formato del body o la estructura de los datos, hubo además un cambio funcional que debe explicarse y probarse.

Preguntas de repaso, con respuesta

  

    
¿El repository tiene que validar el precio?

    
No en esta organización. Esa regla pertenece al service. El repository ofrece acceso a datos.

  

  

    
¿Todas las funciones del service deben tener un if?

    
No. Una consulta simple puede limitarse a delegar. No hace falta inventar una regla para justificar la capa.

  

  

    
¿El DAO puede usar find o filter?

    
Sí. Son herramientas para buscar o eliminar registros del almacenamiento. Decidir si corresponde aumentar una cantidad es una regla distinta y pertenece al service.

  

  

    
¿Puedo usar funciones en vez de clases?

    
Sí. Las capas describen responsabilidades. Se pueden implementar con módulos y funciones, como en estos ejemplos.

  

  

    
Lo que necesitamos poder explicar

    
Ante una petición, debemos poder señalar dónde se recibe el dato, dónde se valida, dónde se busca, dónde se guarda y dónde se responde. Esa comprensión permite reorganizar la API sin perder de vista su funcionamiento.
